Knowledge graph — el saber general
Se basa en nodos (objetos) y aristas (relaciones). Para Cubicup: [Proyecto V-MA89] → aplica → [PGOU Málaga] → gestionado por → [Juan PM].
  • Información estática — los hechos no cambian por el momento del día
  • Da a la IA una base sólida de verdades verificables, elimina alucinaciones
  • Elimina silos: une Monday con Drive con MongoDB en una sola respuesta

Context graph — memoria institucional de decisiones
Concepto de Foundation Capital (dic 2025). El knowledge graph captura qué pasó. El context graph captura por qué pasó.
  • Guarda trazas de decisiones: qué contexto había, qué excepciones se aprobaron, quién decidió qué
  • Con el tiempo forma la memoria institucional real de la empresa
  • Diferencia clave con RAG: RAG recupera documentos. El context graph guarda razonamiento y excepciones
  • Startups cercanas: Zep/Graphiti (temporal knowledge graphs), TrustGraph

RAG vs context graph — la diferencia clave
RAG / retrieval vs context graphComparación
Son complementarios. RAG busca información. El context graph guarda razonamiento. Responden preguntas muy distintas.
+ ver detalle
RAG vs context graph — qué hace cada uno
RAG responde: ¿qué información existe sobre este tema? Busca documentos, los fragmenta, los vectoriza y recupera los más relevantes.

Context graph responde: ¿cómo hemos tomado decisiones similares antes? Guarda trazas de decisiones pasadas con su contexto completo.

Ejemplo Cubicup:
  • RAG: "Busca los planos del proyecto V-MA89" → recupera los PDFs relevantes y los pasa al agente.
  • Context graph: "¿Por qué en proyectos en Málaga siempre pedimos segunda revisión del aparejador?" → guarda que en 8 proyectos anteriores el técnico detectó un patrón de error y creó esa excepción. El agente aprende ese patrón.
RAG es la biblioteca. El context graph es la experiencia acumulada del equipo. Los sistemas más potentes de 2026 combinan ambos.

GraphRAG — la arquitectura que une todoArquitectura
RAG clásico busca texto. GraphRAG navega relaciones del grafo. Para "proyectos en Málaga con licencia pendiente" consulta el grafo directamente. Microsoft Research (2024).
+ ver detalle
GraphRAG — cómo funciona
Navega el mapa de relaciones: Proyecto → está_en_municipio → Málaga, Proyecto → requiere → Licencia, NOT Proyecto → tiene_doc → Licencia_aprobada.
  • Knowledge Graph: extrae entidades de tus sistemas (Cliente, Proyecto, Contrato)
  • Context Graph: integra Monday, Gmail, Calendario para saber en qué trabaja el usuario ahora
  • Resultado: respuestas imposibles de obtener con chatbot genérico o búsqueda en documentos

Las tres disciplinas de ingeniería
2022–2024
Prompt engineering
"Qué decirle al modelo"
Optimiza instrucciones individuales. Opera a nivel de mensaje único.
2025
Context engineering
"Qué mostrarle al modelo"
Diseña el entorno de información. Context window como RAM — qué cargar en cada momento.
2026+
Harness engineering
"Dónde trabaja el modelo"
Diseña el entorno completo: herramientas, límites, feedback loops, guardrails.
Prompt engineering — nivel de mensaje
El arte de formular bien la pregunta. Few-shot learning, chain-of-thought, role-playing.
  • Influye pero no controla — no puede impedir que el agente haga cosas incorrectas
  • Útil para tareas simples. No escala solo en sistemas complejos
cerrar ×
Context engineering — nivel de sesión
Andrej Karpathy (2025): "el arte de llenar el context window con exactamente la información adecuada". Tobi Lütke (Shopify) lo identificó como la skill crítica de su organización.
  • RAG, knowledge graphs y memory son herramientas de context engineering
  • Problema "lost in the middle": los modelos recuerdan mejor el inicio y final del contexto
  • Analogía: el brief ejecutivo curado por un chief of staff — filtra, organiza, prioriza
cerrar ×
Harness engineering — nivel de sistema
Acuñado por Mitchell Hashimoto (co-fundador Terraform) en feb 2026. "Agent = Model + Harness". OpenAI generó 1M líneas de código de producción sin una sola línea manual.
  • Incluye: constraints, feedback loops, guardrails, sandboxes, evals automáticos
  • Stripe genera 1.300 pull requests escritas por AI cada semana con harness bien configurado

Qué hace falta para montarlo
Las piezas necesarias para construir un knowledge graph con capa de agentes. En orden de implementación. Pincha en cada pieza para ver los proveedores.
Antes del código
1. Disciplina de datos
El prerrequisito — ninguna herramienta arregla datos sucios
▾
  • Clave única universal: un ID de proyecto idéntico en Monday, Drive, MongoDB y Holded.
  • Campos bien rellenados: auditar qué campos superan el 80% de completitud.
  • Convención de nombres: tipo_código_fecha.pdf para clasificación automática.
2. Modelo de datos (ontología)
El mapa de entidades y relaciones — el trabajo más importante e infravalorado
▾
  • Entidades: Proyecto, Cliente, Persona, Fase, Documento, Normativa, Hito. Máx 7-8.
  • Relaciones: Proyecto → contrata → Cliente, Proyecto → está_en → Fase.
  • Validación: "¿proyectos en Málaga en HL3 con memoria sin entregar?" Si no responde, el schema está mal.

8. Conectores de datos
Un script por fuente — sincronizan cada sistema con el grafo
▾
  • Monday → Neo4j: API GraphQL, boards HL0-HL4, cron diario. ~4h de ingeniería.
  • Drive / Autodesk Docs → Qdrant: webhook, PyMuPDF, chunking 512 tokens, embeddings. ~6-8h.
  • Holded → Neo4j: REST API, sync diario de facturas. ~3h.
  • Gmail → Neo4j: LLM extrae hitos de threads. Opcional para fase inicial.
  • MongoDB (existente): ya tenéis MCP de lectura — el conector más valioso ya está hecho.
